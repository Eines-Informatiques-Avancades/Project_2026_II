\section{OpenMP Parallelization of Energy Routines}
\label{sec:openmp}

\subsection{\texttt{compute\_total\_energy}: implementation}
 
The $O(N^2)$ LJ pair loop in \texttt{compute\_total\_energy} has
independent iterations and is suitable for OpenMP worksharing. Two
separate \texttt{!\$omp parallel do} regions were written: the LJ loop
uses \texttt{schedule(dynamic,~10)} to compensate for the triangular
iteration space (inner bound varies with \texttt{i}); the torsional
backbone loop uses the default static schedule, which has lower overhead
for a uniform workload. Private variables are declared per region
(\texttt{j}, \texttt{r2} in the LJ region; \texttt{cos\_phi} in the
torsional region), and both accumulators (\texttt{e\_lj}, \texttt{e\_tors})
use a \texttt{reduction(+:...)} clause to prevent data races.
 
The parallelisation is activated at build time via the
\texttt{\_USE\_OPENMP} preprocessor macro, which sets the
\texttt{omp\_total\_energy} flag to \texttt{.true.}. This allows the
same source to compile into a serial or parallel binary without code
changes.
 
\subsection{\texttt{delta\_energy}: implementation}
 
The fixed/moved partitioning reduces the LJ work to a rectangular
$N_\mathrm{fixed} \times N_\mathrm{moved}$ loop. The
\texttt{collapse(2)} directive merges both loop indices into a single
flat iteration space, which OpenMP distributes evenly across threads.
Because pivot moves near the chain termini produce very few moved atoms,
a runtime guard \texttt{if(omp\_delta\_energy .and.\ (n\_fixed*n\_moved > 1000))}
prevents thread-spawn overhead from exceeding the parallel benefit for
small moves.
 
\subsection{Benchmarking: \texttt{compute\_total\_energy}}
 
A dedicated benchmark program performs 10\,000 consecutive calls to \texttt{compute\_total\_energy} on a fixed geometry and reports the total wall time via \texttt{MPI\_Wtime}. The script sweeps thread counts of 1, 2, 3, and 4 across chain sizes of $N = 20,\,50,\,100,\,500$ carbons in all-atom mode. Figure~\ref{fig:omp_total} shows the wall times and parallel efficiency $E = T_1/(p \cdot T_p)$.
 
\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{total_omp_performance.pdf}
  \caption{OpenMP scaling of \texttt{compute\_total\_energy} (10\,000
    evaluations, all-atom model, explicit hydrogens). Left: absolute
    wall time. Right: parallel efficiency $E = T_1/(p\,T_p)$; dashed
    line marks ideal efficiency $E = 1$.}
  \label{fig:omp_total}
\end{figure}
 
Three features stand out. First, at small chain sizes ($N \leq 100$)
adding threads increases wall time -- at $N = 20$, three and four
threads are slower than serial -- confirming that the computation volume
is too small to cover thread-management overhead. Second, even at
$N = 500$ all thread counts converge to essentially the same wall time
($\approx 99$--$104\,\text{s}$), with efficiencies of 0.53, 0.35, and
0.26 for 2, 3, and 4 threads respectively -- well below ideal, with only marginal improvement as $N$ grows.
This indicates that the bottleneck is not arithmetic
but memory bandwidth: the triangular LJ loop accesses coordinate data
in a pattern that generates cache misses, so threads stall waiting for
data rather than executing useful work. The \texttt{is\_excluded}
branch inside the inner loop further fragments the iteration space in
a way that \texttt{schedule(dynamic,~10)} cannot fully correct.
 
\texttt{compute\_total\_energy} is called once at initialisation; the
energy accumulators are subsequently updated incrementally via
$E \leftarrow E + \Delta E$ at each accepted move, so no repeated
full-energy evaluations occur during the MC loop. Given that
parallelisation of this routine yields no measurable benefit, the
\texttt{omp\_total\_energy} flag was disabled for all production
simulations.

\subsection{Benchmarking: \texttt{delta\_energy}}
 
Because \texttt{compute\_total\_energy} is called only at
initialisation, the actual runtime cost of a 1\,M-step simulation is
dominated entirely by \texttt{delta\_energy}. At $N = 500$ with one
thread, the benchmark records $6{,}592\,\text{s}$ for $10^6$ steps,
compared to $0.01\,\text{s}$ for the single \texttt{compute\_total\_energy}
call -- a factor of ${\sim}660{,}000$ difference.
 
The \texttt{delta\_energy} benchmark was run as a full
$10^6$-step MC simulation rather than an isolated call counter,
since that is the context in which the routine operates in
production. Three independent replicas were executed simultaneously
as separate MPI processes, each starting from a different initial
chain configuration. Wall time was recorded per replica using
\texttt{MPI\_Wtime()} and the maximum across all three ranks was
taken as the reported time for each (thread count, chain size)
combination. Thread counts of 1, 2, 3, and 4 were tested across
chain sizes of $N = 50,\,100,\,500$ carbons.
Figure~\ref{fig:omp_delta} shows the results.
 
\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{delta_omp_1000000_steps.pdf}
  \caption{OpenMP scaling of \texttt{delta\_energy} ($10^6$ MC steps,
    all-atom model). Left: absolute wall time. Right: parallel
    efficiency $E = T_1/(p\,T_p)$; dashed line marks ideal $E = 1$.}
  \label{fig:omp_delta}
\end{figure}
 
Unlike \texttt{compute\_total\_energy}, \texttt{delta\_energy} shows
genuine speedup with 2 and 3 threads. Efficiency with 2 threads is
0.60 at both $N = 50$ and $N = 500$, and 0.56 at $N = 100$, giving
wall-time reductions of 11--17\%. With 3 threads the speedup reaches
$1.47$--$1.52\times$ (efficiency $\approx 0.50$) across all chain
sizes, reducing the $N = 500$ simulation from $6{,}592\,\text{s}$ to
$4{,}333\,\text{s}$.
 
Four threads, however, is consistently counterproductive. At $N = 50$
and $N = 100$ the 4-thread run is slower than the serial baseline
(speedup 0.90 and 0.98 respectively), and at $N = 500$ the gain is
negligible (speedup $1.04\times$). The efficiency values of 0.22--0.26
across all sizes indicate that thread-management overhead outweighs
the parallel benefit at this thread count.
 
Notably, the efficiency values are nearly independent of $N$. This is
explained by the \texttt{is\_excluded} branch inside the inner loop:
the number of valid (non-excluded) pairs in the
$N_\mathrm{fixed} \times N_\mathrm{moved}$ space depends on topology,
not simply on $N$, so the effective parallel workload does not scale
uniformly with chain length. The \texttt{collapse(2)} directive assigns
the flat iteration range to threads before knowing which pairs will be
skipped, leaving load imbalance that static scheduling cannot correct.
For 4 threads, synchronization cost and this imbalance together erase
the parallel benefit.

The practical conclusion is that 3 threads is the effective optimum
for \texttt{delta\_energy} (tested on the \texttt{cerqt01.q} cluster queue):
it delivers a consistent ${\approx}1.5\times$ speedup with
${\approx}50\%$ efficiency, reducing the wall time for a $10^6$-step
simulation at $N = 500$ carbons from 6{,}592\,s to 4{,}333\,s -- a
34\% reduction. Four threads provides no benefit on this hardware,
and is slower than serial for smaller chain sizes.

\subsection{SIMD exploration}
 
An attempt was made to exploit single-core SIMD vectorisation on
\texttt{lj\_pair\_energy} with the \texttt{!\$omp declare simd}
directive, processing multiple atom pairs simultaneously in AVX
registers. The \texttt{cycle} on \texttt{is\_excluded} inside the
inner loop is incompatible with SIMD regions, and removing it to
enable vectorisation degraded the load balance provided by
\texttt{collapse(2)}. The directive was removed. Revisiting this is
feasible if the pair loops are refactored to use pre-filtered pair
lists, which would eliminate the exclusion branch entirely.
